# Release v2.0.0.0: Net Types & Multi-Driver Wire Resolution

## 1. Overview & Milestone Scope
This release delivers **v2.0.0.0** of the Cycle Accurate Simulator (CAS), implementing full IEEE Std 1800-2023 compliance for:
- **§6.5 (Net Types & Declarations)**:
  - Full keyword and grammar support for net types: `wire`, `wand`, `wor`, and `tri`.
  - Precise categorization between variables (`reg`, `logic`, `var`, `integer`) and net types (`wire`, `wand`, `wor`, `tri`).
  - Default floating resolution: un-driven nets initialize and float to `'z'` (high-impedance), while variables default to `'x'` (unknown).
  - Single-driver exclusivity enforcement: variables are prohibited from having multiple continuous assignment drivers (`[CAS-MCD]`), whereas net types explicitly permit multiple concurrent continuous drivers.
- **§6.5 & §10.3 (Bitwise 4-State Resolution Functions)**:
  - Strict implementation of IEEE Std 1800-2023 Tables 6-1, 6-2, and 6-3.
  - Multi-driver resolution over arbitrary numbers of concurrent drivers.
- **§10.3 & §10.4.1 (Multi-Driver Continuous Assignment Scheduling & Propagation)**:
  - Unified driver collection: all continuous assignments contributing to the same target net or slice are grouped into `ResolvedContinuousAssign`.
  - Re-evaluation during combinational propagation (`StratifiedScheduler::propagate_comb`): all active drivers for each multi-driven net are re-evaluated, bit-extended to the target width, and combined using the net's specific resolution function.
  - Reactive downstream fanout propagation: delta cycles loop reactively whenever a resolved multi-driver net changes value, propagating through slice bindings and subsequent continuous assignments.

## 2. IEEE Std 1800-2023 Resolution Truth Tables

### Table 6-1: `wire` and `tri` Resolution
`wire` and `tri` share identical resolution semantics. High-impedance `z` yields to any driven value; conflicting driven levels resolve to `x`.

| Driver 1 \ Driver 2 | 0 | 1 | x | z |
|:---:|:---:|:---:|:---:|:---:|
| **0** | `0` | `x` | `x` | `0` |
| **1** | `x` | `1` | `x` | `1` |
| **x** | `x` | `x` | `x` | `x` |
| **z** | `0` | `1` | `x` | `z` |

### Table 6-2: `wand` and `triand` Resolution (Wired AND)
In wired-AND configurations, `0` dominates over all other logic states (including `x` and `z`). High-impedance `z` acts as a neutral pull-up.

| Driver 1 \ Driver 2 | 0 | 1 | x | z |
|:---:|:---:|:---:|:---:|:---:|
| **0** | `0` | `0` | `0` | `0` |
| **1** | `0` | `1` | `x` | `1` |
| **x** | `0` | `x` | `x` | `x` |
| **z** | `0` | `1` | `x` | `z` |

### Table 6-3: `wor` and `trior` Resolution (Wired OR)
In wired-OR configurations, `1` dominates over all other logic states (including `x` and `z`). High-impedance `z` acts as a neutral pull-down.

| Driver 1 \ Driver 2 | 0 | 1 | x | z |
|:---:|:---:|:---:|:---:|:---:|
| **0** | `0` | `1` | `x` | `0` |
| **1** | `1` | `1` | `1` | `1` |
| **x** | `x` | `1` | `x` | `x` |
| **z** | `0` | `1` | `x` | `z` |

## 3. Key Architecture Achievements & Refactorings

### A. Frontend Lexical & AST Grammar
- **Tokens (`lexer.hpp`, `lexer.cpp`)**:
  - Added `TOKEN_WAND` (`wand`), `TOKEN_WOR` (`wor`), and `TOKEN_TRI` (`tri`) to `TokenType` alongside `TOKEN_WIRE`.
- **Type Enumeration (`net_types.hpp`, `types.hpp`)**:
  - Introduced `enum class NetKind { WIRE, WAND, WOR, TRI, VAR };`.
- **AST Nodes (`ast_module.hpp`, `parser_module.cpp`)**:
  - Extended `PortNode` with `NetKind net_kind = NetKind::WIRE;`.
  - Updated ANSI header port parser, non-ANSI port declaration parser, and internal signal declaration parser to tag nets and variables with their appropriate `NetKind`.

### B. High-Performance 4-State Bitwise Resolution Engine (`logic_ops.hpp`)
- Implemented branchless, 64-bit parallel resolution primitives:
  - `LogicOps::resolve_wire(a, b)`: Implements Table 6-1 using bitplane care masks.
  - `LogicOps::resolve_wand(a, b)`: Implements Table 6-2 with dominant zero masking.
  - `LogicOps::resolve_wor(a, b)`: Implements Table 6-3 with dominant one masking.
  - `LogicOps::resolve_net(kind, a, b)`: Dispatches to the corresponding resolution primitive based on `NetKind`.

### C. Kernel Elaboration & Driver Exclusivity Enforcement (`elaborator.hpp`, `elaborator.cpp`, `engine.hpp`, `engine.cpp`, `scheduler.cpp`)
- **Net Initialization (`netlist.hpp`, `elaborator.cpp`)**:
  - `Net` tracks `NetKind kind`.
  - Automatically initializes `NetKind::VAR` variables to `'x'` and net types (`WIRE`, `WAND`, `WOR`, `TRI`) to `'z'`.
- **Driver Exclusivity Verification (`elaborator.cpp`)**:
  - Distinguishes variables from nets during elaboration. Multiple continuous assignments driving a variable trigger compile-time rejection:
    `[CAS-MCD] Illegal combination of continuous drivers: variable '<name>' cannot be driven by multiple continuous assignments.`
  - Nets (`wire`, `wand`, `wor`, `tri`) permit multiple continuous assignment drivers and proceed to resolution aggregation.
- **Continuous Assignment Grouping (`engine.cpp`)**:
  - In `Engine::load_elaboration()`, compiles flat `continuous_assigns` into `resolved_continuous_assigns` indexed by unique slice key (`net_id`, `offset`, `width`).
- **Combinational Propagation Pass (`scheduler.cpp`)**:
  - In `StratifiedScheduler::propagate_comb()`, evaluates all drivers contributing to each `ResolvedContinuousAssign` and applies multi-driver resolution. Updates target nets and triggers delta cycles upon value transitions.
