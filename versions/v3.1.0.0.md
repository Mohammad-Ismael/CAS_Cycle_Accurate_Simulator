# Release v3.1.0.0: Interface Modports, Directional Modport Port Typings, and Modport Connection Bindings

## 1. Overview & Milestone Scope
This release delivers **v3.1.0.0** of the Cycle Accurate Simulator (CAS), advancing simulator maturity to **23.5%** and implementing full IEEE Std 1800-2023 compliance for:
- **§25.5.3 (Interface Modports)**:
  - Declarations of modports within interface declarations (`modport modport_name ( [direction] signal_list, ... );`) establishing directional views of interface members.
  - Multi-direction groups per modport supporting `input`, `output`, and `inout` port lists.
  - Multiple modport declarations within a single interface scope (e.g. `modport master (...)`, `modport slave (...)`).
- **§25.5.3 (Directional Modport Port Typings)**:
  - Modules declaring interface ports explicitly constrained by a modport view (`module bus_producer (simple_bus_if.master bus, ...);`).
  - Separation of interface base type and modport view identifier (`interface_name.modport_name`).
- **§25.5.3 (Modport Connection Bindings)**:
  - Explicit modport selection at instance port connection (`.bus(bus.master)`), parsed as a hierarchical member expression and bound to the underlying interface instance.
  - Directional mapping and tracking in elaboration result (`modport_binding_map`).
  - Seamless procedural reads, writes, and event control sensitivity through modport views.

## 2. IEEE Std 1800-2023 Semantics & Mechanics

### A. Modport AST Nodes (`CAS/include/frontend/ast_module.hpp`)
- `ModportItemNode` represents each modport declaration and stores its directional port list:
  ```cpp
  struct ModportPort {
      std::string direction; // "input", "output", "inout"
      std::string name;
  };

  struct ModportItemNode : public ASTNode {
      std::string name;
      std::vector<ModportPort> ports;
      std::unordered_map<std::string, std::string> port_directions;

      ModportItemNode(std::string n) : name(std::move(n)) {}
      void add_port(const std::string& dir, const std::string& port_name) {
          ports.push_back({dir, port_name});
          port_directions[port_name] = dir;
      }
  };
  ```
- `ModuleNode` stores modports in `std::vector<std::unique_ptr<ModportItemNode>> modports` and provides `std::unordered_map<std::string, ModportItemNode*> modport_map`.
- Formal `PortNode` stores:
  ```cpp
  std::string modport_name; // E.g., "master" or "slave"
  ```

### B. Frontend Lexer & Parser Updates
- Added `TOKEN_MODPORT` (`modport`) keyword recognition to lexer (`CAS/include/frontend/lexer.hpp`, `CAS/src/frontend/lexer.cpp`).
- Updated `CAS/src/frontend/parser_module.cpp`:
  - Parses modport definitions inside interfaces:
    ```systemverilog
    modport master (
        input  clk, ready,
        output valid, data
    );
    ```
  - Parses modport-typed module port headers:
    ```systemverilog
    module bus_producer (
        simple_bus_if.master bus,
        input  logic         rst_n,
        ...
    );
    ```
    Records `port.interface_type_name = "simple_bus_if"`, `port.modport_name = "master"`, and `port.type_name = "simple_bus_if.master"`.

### C. Elaboration & Modport Binding (`CAS/src/kernel/elaborator.cpp`)
- `ElaborationResult` and `Engine` record:
  ```cpp
  std::unordered_map<std::string, std::string> modport_binding_map;
  ```
- When elaborating module instances, if the connection expression is a `MemberAccessNode` (e.g. `.bus(bus.master)`), the elaborator extracts:
  - Base interface instance identifier: `actual_iface_name = mem->var_name` (`"bus"`)
  - Bound modport view: `modport_view = mem->member_name` (`"master"`)
- If `.bus(bus)` is passed and formal port defines a modport type (e.g. `simple_bus_if.master`), `modport_view` defaults to `formal_p->modport_name`.
- Maps child port `tb_v3_1_0_0_regression.u_producer.bus` to parent interface instance `tb_v3_1_0_0_regression.bus` in `result.interface_port_map`.
- Stores modport view `result.modport_binding_map["tb_v3_1_0_0_regression.u_producer.bus"] = "master"`.
