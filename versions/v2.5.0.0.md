# Release v2.5.0.0: Enumerated Types, Typedefs, and Built-in Methods

## 1. Overview & Milestone Scope
This release delivers **v2.5.0.0** of the Cycle Accurate Simulator (CAS), implementing full IEEE Std 1800-2023 compliance for:
- **§6.19 (Enumerated Types & Typedef Declarations)**:
  - Keyword and grammar support for `typedef enum`:
    ```systemverilog
    typedef enum [base_type] {
        NAME1 [= val1],
        NAME2 [= val2],
        ...
    } type_name_t;
    ```
  - Base type handling: Defaults to `int` (32-bit signed) when omitted; supports explicit base types (e.g., `logic [1:0]`, `byte`, `integer`, etc.) with user-defined width and signedness.
  - Automatic ordinal assignment: Unassigned members automatically increment from the preceding member (+1), defaulting to 0 for the first member.
  - Constant scope visibility: Enum member identifiers become valid constant expressions accessible directly in expressions, continuous assignments, procedural blocks, and selection statements (`case`/`casex`/`casez`).
- **§6.19.5 (Built-in Enumeration Methods)**:
  - `.first()`: Returns the first member value in the enumeration definition.
  - `.last()`: Returns the last member value in the enumeration definition.
  - `.next([N=1])`: Returns the N-th next enumeration value (defaulting to 1). Wraps around cleanly to the start when reaching the end. Returns `.first()` if called on a value outside the enum definition.
  - `.prev([N=1])`: Returns the N-th previous enumeration value (defaulting to 1). Wraps around cleanly to the end when reaching the beginning. Returns `.last()` if called on a value outside the enum definition.
  - `.name()`: Returns a string literal representing the member name corresponding to the variable's current value. Returns an empty string `""` if the value is not a valid enum member.
- **§6.24 (Type Casting)**:
  - Static type casting using the apostrophe cast operator: `type_name'(expression)`.
  - Casts the evaluated expression to the target enum type width and signedness.

## 2. IEEE Std 1800-2023 Semantics & Mechanics

### A. Enumeration Definition & Scope Symbol Table
- Enumeration types declared at module or file scope are parsed into `EnumTypeNode` AST nodes and registered in `Parser::typedef_map`.
- During elaboration, `Elaborator` registers enum definitions into `Engine::enum_types` and populates `Engine::enum_constant_map`:
  ```cpp
  struct EnumMember {
      std::string name;
      LogicVal val;
  };

  struct EnumType {
      std::string name;
      uint32_t width = 32;
      bool is_signed = false;
      std::vector<EnumMember> members;
      ...
  };
  ```
- Variables declared with an enum typedef name (e.g., `state_t current_state, next_state;`) are instantiated as `NetKind::VAR` with their base type's width, signedness, and an attached `type_name` tag mapping to `Engine::var_to_enum_type`.

### B. Built-in Method Dispatch & Evaluator Execution
- When `.method()` is invoked on an enum variable (represented via `MethodCallNode` in AST):
  1. The variable's associated enum type is resolved via `var_to_enum_type` or `LocalVar::type_name`.
  2. The current 4-state value of the target variable is evaluated.
  3. The requested method is executed:
     - `.name()` returns a `LogicVal` marked with `is_string = true` and populated with the member's string name.
     - `.first()` returns the first declared `EnumMember::val`.
     - `.last()` returns the final declared `EnumMember::val`.
     - `.next(N)` and `.prev(N)` compute wrapped ordinal shifts modulo member count.

### C. String Logic Values & Output Formatting (§21.2)
- Extended `LogicVal` to carry `is_string` and `str_val` payload.
- Extended `$display` and `$monitor` formatting engines in `Evaluator`:
  - Added support for the `%s` format specifier.
  - `$monitor` dynamically monitors complex expressions including method calls (such as `tb_state.name()`), triggering Postponed sampling whenever watched values or string representations update.

## 3. Key Architectural Achievements & Refactorings

### A. Frontend Lexer & AST Grammar
- **Tokens (`lexer.hpp`, `lexer.cpp`)**:
  - Added `TOKEN_TYPEDEF` (`typedef`), `TOKEN_ENUM` (`enum`), and `TOKEN_APOSTROPHE` (`'`).
  - Differentiated standalone tick tokens from unbased unsized literals (`'0`, `'1`, `'x`, `'z`).
- **AST Nodes (`ast_expr.hpp`, `ast_stmt.hpp`, `ast_module.hpp`)**:
  - Added `EnumTypeNode` and `TypedefNode` in `ast_module.hpp`.
  - Added `MethodCallNode`, `CastNode`, and `StringNode` in `ast_expr.hpp`.
  - Extended `PortNode` and `VarDeclStatementNode` to store `type_name`.
- **Parser (`parser_module.cpp`, `parser_stmt.cpp`, `parser_expr.cpp`)**:
  - Implemented `Parser::parse_typedef()` handling base types, ranges (`[msb:lsb]`), member list parsing, and automatic values.
  - Added variable declaration parsing for typedef identifiers in module bodies and procedural scopes.
  - Implemented method call parsing (`ident.method(args)`), static type casting (`type'(expr)`), and string literal expression parsing.

### B. Kernel Elaborator & Netlist Binding (`elaborator.hpp`, `elaborator.cpp`, `netlist.hpp`)
- Added `type_name` tracking to `Net` in `netlist.hpp` and `LocalVar` in `execution_context.hpp`.
- Populated `enum_types`, `var_to_enum_type`, and `enum_constant_map` during hierarchical module elaboration.
- Resolved enum constant identifiers directly during constant expression elaboration.

### C. Stratified Scheduler & Evaluator Engine (`evaluator.cpp`, `expr_evaluator.cpp`)
- Integrated `MethodCallNode`, `CastNode`, and `StringNode` into `ExprEvaluator::eval()`.
- Implemented string comparisons in `BinaryOpNode` (`==`, `!=`, `===`, `!==`).
- Updated `MonitorSession` to store and evaluate arbitrary AST expression trees across simulation time slots in the Postponed region.
